# 复核记录

## 第一轮

提交 `e68e9bc`（Add the scheduler core, hand-calculated tests, and a first visualizer）。

这一轮把调度核心和基本界面分开：

- `SchedulerEngine` 按离散时刻跑 FCFS、非抢占 SJF、SRTF、RR、优先级非抢占、优先级抢占、至少 3 级的 MLFQ。
- 进程有 PID、到达、服务、优先级、剩余时间，状态覆盖新建、就绪、运行、等待、完成。
- 用例 A（错开到达）、B（同时到达）、C（单进程）以及时间片为 1、平局不抢占、严格更优才抢占、SJF 的到达时间/PID 平局，都写进 `tests/fixtures/standard-cases.json`，单元测试直接比较片段和四个时间指标。
- 界面能切算法、单步、调速度、看甘特图、就绪队列、状态历史和指标，并能导出 JSON/CSV、并排对比。

本轮结束时还没有浏览器测试、CI 和完整说明。README 只有一行「见后续修订」。

## 第二轮

对照手算把用例 A 的七种算法、用例 B/C 和边界夹具又推了一遍。片段、完成时间、周转、等待、响应与夹具一致，没有为了让测试变绿而改预期。这一轮修的是会让手算和屏幕对不上、或让等待态看不出来的问题。

1. **标准用例会沿用上一次的时间片。** 点过「时间片为 1」再加载用例 A，RR 仍是 q=1，MLFQ 也不回到 2/4/8。屏幕上的用例 A 就会和 README 里的手算不同。用例 A/B/C 现在固定恢复 q=2 和 MLFQ 2/4/8，不改当前选中的算法。单元测试锁住预设字段，端到端测试先把时间片改成 1、把 MLFQ 改成 3/3/3，再加载用例 A，确认甘特图回到 q=2 的手算片段。

2. **甘特图和核心片段的对应靠颜色块，短片段看不清区间。** 服务时间为 1 的块以前不标区间；同一进程连续两次分派也容易看成一段。现在每块标出起止，图下印出与核心相同的片段串（`P1[0,2) P1[2,4)` 这种不合并）。同色块之间留出空隙，并写明这是再次分派，不是空闲。端到端测试同时比对 DOM 上的 `data-start`/`data-end` 和图下文字。

3. **等待态只出现在下方历史文字里。** I/O 示例的截图原来是跑完以后截的，当时 CPU 显示空闲，是因为仿真结束，不是因为阻塞。现在就绪队列旁边有「等待（I/O）」。端到端测试在 t=2 停下：P1 处于等待，P2 在队首，卡片说明下一步才分派 P2；再跑完后检查 `P1[0,2) P2[2,5) P1[5,7)`，以及 P1 等待时间为 0（阻塞不计入）。

4. **时间片边界上 CPU 持有者已经清空，队首进程要到下一拍才上台。** 卡片以前只写「空闲」，看起来像漏了一次分派。若队首已有进程，现在写明下一拍分派的是谁；若到达时刻正好是当前时钟、进程还是新建态，写明下一步才入队。

5. **对比图太窄，而且不说明用的时间片。** 对比甘特图加宽到能标出长度为 2 的区间，页头写明 RR 与 MLFQ 的时间片，并提示改完要重新生成。并排图下的片段文字也和夹具比较。

6. **CSV 的汇总行把完成时刻塞进 `slice_end`。** 现在有单独的 `makespan` 列，`cpu_utilization` 仍是 0 到 1 的比值。单元测试锁住用例 FCFS-PID 那一行的 15 列。

7. **边界夹具只在 `edges.test.ts` 里跑。** FCFS、SJF、SRTF、RR、优先级和 MLFQ 各自的测试文件现在也锁定自己的边界用例，避免只看算法文件时漏掉平局规则。

8. **没有端到端测试和 CI。** 补上 Playwright，以及只在本目录或工作流改动、且仅 `pull_request` 时触发的 GitHub Actions：干净安装、中文字体、Chromium、类型检查、单元测试、构建、端到端，并上传报告和截图。

9. **README 不能用来手算。** 换成调度合同、七种算法的平局和抢占规则、用例 A 的逐步队列、A/B/C 的对照表、边界表、动态添加和 I/O 的数字，以及测试命令和已知限制。

没有改夹具里的完成时间或片段去迎合实现。第二轮对引擎行为的改动是导出列，不是调度顺序。

## 第三轮

这一轮加上 HRRN、可选的优先级老化、可选的 MLFQ 周期性提升、可配置的上下文切换、JSON/CSV 导入、按种子生成进程、时间轴回看，以及对比柱状图和对比 CSV/HTML。默认关闭切换、老化和提升。用例 A/B/C 的进程、片段和四个时间指标没有改。

核对新用例时先发现的是手算，不是引擎：

1. **抢占老化在 t=9 的平局写错了。** 用例 D 里 P3 在 t=9 到达，原始优先级 2。同一时刻 P1 已经在就绪态等了 4，老化间隔 2，有效优先级也是 2，而且比 P3 更早到达。正确决定是 P1 上台，不是 P3。按这个规则把后面的 t=11、t=13、t=15、t=19 重算之后，片段是 `P1[0,5) P2[5,9) P1[9,11) P3[11,13) P1[13,15) P2[15,19) P1[19,20) P2[20,22)`。P3 的完成时间是 13，等待 2，响应 2。引擎原本就是这样，夹具改成了重算后的表，没有为了迁就第一版手算去改比较器。

2. **结束校验只减了切换时间，没有对上甘特图。** `assertComplete` 已经用「完成 − 到达 − 服务 − I/O − 切换 = 就绪等待」检查每个进程，但没检查切换段的总长度等于各进程 `switchTime` 之和。第一次补这段检查时，循环头 `for (const proc of this.procs)` 在文件里出现了两次，替换没有落上。后来用甘特图结尾那一段上下文补进了 `assertComplete`。c=1 的 FCFS、RR 和「只剩自己也要再付切换」都会走到它。

3. **提升日志要等那一拍真正执行。** 时钟停在 t=4、还没执行这一拍时，提升还没发生，未到达进程仍是新建，日志里也还没有「周期性提升」。提升写在该拍 `schedule` 的开头，先于这一拍的到达。测试改成先看 t=4 之前的新建态，再走一拍，确认日志和到达。这是观察点和引擎顺序的差别，不是把提升提前到上一拍。

4. **同一个进程的最终有效优先级不能拿来证明「运行中不老化」。** 老化间隔为 1、两人优先级相同的时候，等待的那个会在下一拍变得严格更好，把正在运行的进程抢下来。被抢者随后自己也在等待，结束时的有效优先级当然变了。测试改成在它还在运行的两拍里读快照：就绪等待是 0，有效优先级仍是原始值。

5. **HRRN 插进算法目录后，对比导出会多一种算法。** 目录顺序是 FCFS、SJF、SRTF、RR、两种优先级、HRRN、MLFQ。对比如果默认全选，原来锁住的七种算法导出顺序会在优先级抢占和 MLFQ 之间多出 `hrrn`。界面默认不勾选 HRRN，生成时仍按目录顺序过滤，七种算法的导出顺序不变。端到端测试确认默认报告没有 HRRN 行，CSV 里也没有 `hrrn`。

6. **切换开销会沿用到下一次标准用例，和上一轮的时间片泄漏是同一类问题。** 预设以前只在字段有值时才写时间片。若加载用例 E 后再加载用例 A，A 没有写切换开销，c=1 就会留着，用例 A 的甘特图会多出切换段。现在每次加载预设都写切换、老化和提升；A/B/C/Q1/I/O 没写时用 0。端到端测试先跑 c=1 的 FCFS 和 RR，再加载用例 A，确认切换开销回到 0，FCFS 片段回到原来的手算。

7. **切换段如果按 pid 为空来画，就会和空闲长得一样。** 核心的片段文字已经把 `switch: true` 印成「切换」，但图上凡是 pid 为空都用空闲斜线，测试读到的 `data-pid` 也会是 `idle`。c=1 的图下写着切换，色块却像空闲。现在切换用另一组斜线，`data-pid="switch"`，图例分开写「切换」和「空闲」。

8. **「运行至结束」只留下起点和终点两张快照。** 循环里每一步都改了引擎，但只在循环结束后发布一次。时间轴的最大值是完成时刻，中间时刻没有记录，拖到 3 时找不到快照，受控滑块又弹回终点。现在每走一步都记下当时的就绪队列、运行进程和指标。回看用例 A 的 t=3 时，P1 仍在运行，P2 在队首，P2 的等待是 1。

界面上的指标句子也改了：等待要减去切换开销，利用率的分子只算服务时间。c=0 时切换开销是 0，所以这句新定义不会改用例 A/B/C 的数字。

没有删除或放宽原有的 88 个单元测试和 14 个端到端测试，也没有改 `standard-cases.json` 里的数字。新增预期在 `round3-cases.json`，新增单元测试在 `tests/unit/round3.test.ts`。
