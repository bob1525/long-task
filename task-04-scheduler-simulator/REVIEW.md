# 复核记录

## 第一轮

提交 `e68e9bc`（Add the scheduler core, hand-calculated tests, and a first visualizer）。

这一轮把调度核心和基本界面分开：

- `SchedulerEngine` 按离散时刻跑 FCFS、非抢占 SJF、SRTF、RR、优先级非抢占、优先级抢占、至少 3 级的 MLFQ。
- 进程有 PID、到达、服务、优先级、剩余时间，状态覆盖新建、就绪、运行、等待、完成。
- 用例 A（错开到达）、B（同时到达）、C（单进程）以及时间片为 1、平局不抢占、严格更优才抢占、SJF 的到达时间/PID 平局，都写进 `tests/fixtures/standard-cases.json`，单元测试直接比较片段和四个时间指标。
- 界面能切算法、单步、调速度、看甘特图、就绪队列、状态历史和指标，并能导出 JSON/CSV、并排对比。

本轮结束时还没有浏览器测试、CI 和完整说明。README 只有一行「见后续修订」。

## 第二轮

对照手算把用例 A 的七种算法、用例 B/C 和边界夹具又推了一遍。片段、完成时间、周转、等待、响应与夹具一致，没有为了让测试变绿而改预期。这一轮修的是会让手算和屏幕对不上、或让等待态看不出来的问题。

1. **标准用例会沿用上一次的时间片。** 点过「时间片为 1」再加载用例 A，RR 仍是 q=1，MLFQ 也不回到 2/4/8。屏幕上的用例 A 就会和 README 里的手算不同。用例 A/B/C 现在固定恢复 q=2 和 MLFQ 2/4/8，不改当前选中的算法。单元测试锁住预设字段，端到端测试先把时间片改成 1、把 MLFQ 改成 3/3/3，再加载用例 A，确认甘特图回到 q=2 的手算片段。

2. **甘特图和核心片段的对应靠颜色块，短片段看不清区间。** 服务时间为 1 的块以前不标区间；同一进程连续两次分派也容易看成一段。现在每块标出起止，图下印出与核心相同的片段串（`P1[0,2) P1[2,4)` 这种不合并）。同色块之间留出空隙，并写明这是再次分派，不是空闲。端到端测试同时比对 DOM 上的 `data-start`/`data-end` 和图下文字。

3. **等待态只出现在下方历史文字里。** I/O 示例的截图原来是跑完以后截的，当时 CPU 显示空闲，是因为仿真结束，不是因为阻塞。现在就绪队列旁边有「等待（I/O）」。端到端测试在 t=2 停下：P1 处于等待，P2 在队首，卡片说明下一步才分派 P2；再跑完后检查 `P1[0,2) P2[2,5) P1[5,7)`，以及 P1 等待时间为 0（阻塞不计入）。

4. **时间片边界上 CPU 持有者已经清空，队首进程要到下一拍才上台。** 卡片以前只写「空闲」，看起来像漏了一次分派。若队首已有进程，现在写明下一拍分派的是谁；若到达时刻正好是当前时钟、进程还是新建态，写明下一步才入队。

5. **对比图太窄，而且不说明用的时间片。** 对比甘特图加宽到能标出长度为 2 的区间，页头写明 RR 与 MLFQ 的时间片，并提示改完要重新生成。并排图下的片段文字也和夹具比较。

6. **CSV 的汇总行把完成时刻塞进 `slice_end`。** 现在有单独的 `makespan` 列，`cpu_utilization` 仍是 0 到 1 的比值。单元测试锁住用例 FCFS-PID 那一行的 15 列。

7. **边界夹具只在 `edges.test.ts` 里跑。** FCFS、SJF、SRTF、RR、优先级和 MLFQ 各自的测试文件现在也锁定自己的边界用例，避免只看算法文件时漏掉平局规则。

8. **没有端到端测试和 CI。** 补上 Playwright，以及只在本目录或工作流改动、且仅 `pull_request` 时触发的 GitHub Actions：干净安装、中文字体、Chromium、类型检查、单元测试、构建、端到端，并上传报告和截图。

9. **README 不能用来手算。** 换成调度合同、七种算法的平局和抢占规则、用例 A 的逐步队列、A/B/C 的对照表、边界表、动态添加和 I/O 的数字，以及测试命令和已知限制。

没有改夹具里的完成时间或片段去迎合实现。第二轮对引擎行为的改动是导出列，不是调度顺序。
